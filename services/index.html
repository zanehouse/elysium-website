Most firms buying AI infrastructure don’t need it.

I audit where AI actually fits inside a boutique bank, prove the hours saved against past deal work, and build only what survives that test.

Two Expensive Defaults

The Problem

What does an outright ban on AI actually stop? Not much. Analysts still need to summarize a two hundred page CIM by Monday morning, so a ban does not remove the incentive to use these tools, it just removes the paper trail. The realistic outcome is analysts pasting cap tables and diligence documents into personal accounts on personal devices, off the firm’s network, with no data processing agreement and no log of what left the building. That is a worse outcome than sanctioned use, not a safer one.

The other default is no better. Firms that turn on an AI tool without governance typically hand every employee the same account, tied to no deal code and no permission tier. A confidential information memorandum from one live deal sits in the same query history as a comp set pull for another, which means an analyst on one deal now has technical access to whatever an analyst on a walled-off deal queried that week. That is an information barrier failure that would draw immediate scrutiny if it happened on paper; it draws none because it happened inside a chat window.

Both defaults produce the same exposure: MNPI moving through a system nobody can audit, at a firm whose entire business model depends on the market believing MNPI never moves that way. Fixing that is not a policy memo. It requires deciding, process by process rather than firm-wide, where each one runs and who can see the output.

The Engagement

Audit

Phase One

The audit inventories every recurring process at the firm: CIM review, comp set construction, NDA turnaround, diligence checklist triage, LBO model formatting, board deck production, and whatever else is eating analyst hours. Each process is scored against five criteria and ranked by expected hours saved against the effort required to build it. The firm walks away with a written report ranking every process, the current hours cost of each one measured against its own deal history, and a shortlist of what to build first. Nothing in the audit requires committing to the build phase; the report stands on its own.

Build

Phase Two

The build phase implements the top one to three processes from the audit as working tools, deployed on whichever infrastructure fits that process’s data classification. Each build ships with documentation and a training session, so the deal team runs it without a specialist on call. The firm ends the engagement holding a functioning pipeline it owns, not a subscription to a black box; if the retainer ends, the build keeps running.

Retainer

Phase Three

The retainer covers what changes after the build ships. It adds new processes to the queue as the firm’s deal mix shifts, reevaluates model versions as vendors update them, and maintains the governance policy as new tools enter scope. It also covers on-call support when a compliance officer or an MD has a question about a specific query or output. Pricing for all three phases sits behind a call, since the labor cost of the audit itself depends on firm size and process count.

Score Every Process Before Building Anything

The Scoring Framework

The audit weighs every process against five criteria: volume, labor cost, error tolerance, input structure, and variance. Volume asks how often the process runs in a given quarter. Labor cost asks how many analyst hours the process currently costs; the audit measures that number against the firm’s own timesheets and deal logs rather than an industry estimate. Error tolerance asks what happens downstream if the output is wrong, since a formatting error in a comp set is a five minute fix while a wrong number in a fairness opinion is a legal problem. Input structure asks whether the source material is machine readable, like a cap table in a spreadsheet, or judgment heavy, like a redline against a counterparty’s paper. Variance asks how much the process changes from deal to deal, since a workflow that looks different every time is harder to automate reliably than one that repeats the same shape.

The highest-stakes process at any bank is arguably the worst place to start. A fairness opinion or a purchase agreement redline scores high on labor cost and gets everyone’s attention, though it also scores low on error tolerance and high on variance, which means the automation is hardest to trust and most expensive to get wrong. The better first targets score high on volume and structure and moderate on stakes: an initial CIM summarization pass, a comp set pull and formatting job, or a first-round NDA review. Those processes run often, follow a repeatable shape, and produce output a human reviews before it reaches a counterparty anyway.

Public API, Private Cloud, or On-Prem

Deployment Options

Every build runs on one of three infrastructures: a public API under enterprise terms, a private cloud deployment, or on-premise hardware. Enterprise API terms from a frontier lab include zero data retention, meaning the vendor does not store prompts and outputs or use them for training, along with tenant isolation and, for regulated clients, data residency guarantees. Private cloud deployment runs the same class of model inside infrastructure dedicated to the firm, which suits processes where a client or a regulator specifically requires that data never leave a controlled environment. Most boutique banks land on one of these two options once they see the contract terms in writing, because the confidentiality guarantee they were trying to solve for with hardware already exists on paper.

On-prem is rarely the right answer, and firms considering it should hear the real reasons before signing a hardware order. The open-weight models that run on infrastructure a bank can own trail the frontier models available through an API by a meaningful margin, so the firm is trading model quality for a sense of control it does not need. The hardware itself depreciates fast—most of its resale value is gone within eighteen to twenty-four months—while the enterprise contract terms above update automatically as the vendor improves them. When the server room has a problem the night before a close, there is no SLA, no support line, and no one to call; the firm is on its own with hardware it bought specifically to avoid depending on anyone else.

The Part Most Firms Skip

Governance

Governance is the part most firms skip, and it is the part that actually answers the confidentiality question. It starts with data classification: every document a firm touches is public, confidential, or MNPI, and that classification determines which deployment option can hold it and which employees can query it. Governance scopes tool access to deal teams the same way firms already scope physical access, so an analyst on one live deal cannot reach the model history or documents tied to another. The system logs every query against a deal code, so the firm can answer, precisely, who asked a model about what and when.

That combination becomes a written policy the compliance officer can actually file: a document specifying data classification rules, deal team permissions, retention terms, and logging requirements, in language a regulator or an auditor can read without a translator. Most firms currently have either no policy or a policy borrowed from a vendor’s marketing page, neither of which holds up under review. Building the real one is part of the retainer, and it is usually the deliverable compliance signs off on before anyone touches a live deal.
